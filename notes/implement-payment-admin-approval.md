# Implementation prompt: payment → review → shipping

Update the existing FraudShield portal so payment records a booking request, and an administrator must approve that booking before shipping can begin.

1. Preserve the customer portal, seven-step wizard, admin investigation screen, typed service layer, and existing trained-model files.
2. After successful payment confirmation, create exactly one booking with a payment receipt and the status **Awaiting Approval**, regardless of its risk score. Show the customer “Payment complete — awaiting admin approval.” Keep physical shipping at Created until an administrator releases it. Payment failure must not create a paid booking.
3. Place the booking in the administrator’s approval queue with all sender/receiver, package, collection, protection, payment, and risk details. Show the rule score separately from the model score. Identify the score source accurately; never present simulated output as an actual trained-model result. If scoring is unavailable, show that state explicitly.
4. Require an authenticated admin session, a reason, and confirmation to approve, hold, or block. Retain risk evidence and all prior decisions. Approval permits shipping but does not claim a pickup happened. Holding or blocking prevents dispatch. Rejection does not imply a refund has occurred.
5. Enforce the dispatch prerequisite in the service layer: paid booking + admin approval + ready evidence. Prevent stale decisions, duplicate submission, duplicate dispatch, and edits that silently invalidate an approval. Keep already-dispatched shipment decisions read-only.
6. Keep the customer waiting screen, shipment table, tracking timeline, dashboard, inbox, admin queue, and audit view synchronized, including across browser tabs. Preserve existing locally saved demo data with an explicit migration.
7. Connect the saved LightGBM model, as selected by the user, through a read-only scoring adapter. Keep UI demonstration authentication/payment clearly labeled. Do not integrate a real payment gateway or claim production authorization guarantees from frontend code. Preserve clearly labeled seeded sample scores. Real model integration must respect its feature contract and disclose unsupported portal inputs rather than inventing a probability; missing model output must disable approval.
8. Add focused tests for low- and high-risk bookings awaiting approval, duplicate confirmation, rejected payment, customer access restrictions, approval/hold/block transitions, dispatch gating, score failure, stale revisions, evidence retention, persistence, and cross-tab refresh. Build and check the implementation. Report any verification limitations.
